# Long-running tools, jobs, and loop continuation

**Goal.** Agent-loop can launch a CLI operation that takes 30 minutes, keep the CLI responsive, monitor execution without spending model turns on polling, report completion, collect the result, and continue the same agent loop. Build this first for RGBA video generation. Schedules, voice clients, and child agents use the same lifecycle later. This document is a plan; these capabilities are not implemented yet.

**Today.** [Runtime.run](../agent_loop/runtime.py) blocks in `communicate()` and kills the process group on timeout; [shell_run](../agent_loop/tools.py) defaults to 30 seconds. Raising that timeout keeps the tool call blocked. [The CLI](../agent_loop/__main__.py) runs the loop synchronously, waits for keyboard input between interactive turns, and tears down the runtime after a one-shot task. [The loop](../agent_loop/loop.py) has no completion inbox and treats `done` as success even when its answer reports inability. Background execution needs a retained task handle, an independent monitor, and a wake path into the conversation.

Handle three submission shapes, based on the returned payload rather than the action name:

- **One remote job:** retain `job_id`, including receipts already marked completed or failed. Poll `rgba jobs get <id> --json`, or the equivalent HTTP endpoint through the [RGBA adapter](RGBA.md). For example, submit `rgba sdk generate-shots --params '{"video_id":"<id>"}' --no-wait --json` and register the returned receipt.
- **A remote job group:** Replicate batch dispatch can return `jobs: [{shot_id, job_id}, ...]` plus immediate `failed` entries. Retain every ID and submission failure, collect each result, and aggregate the outcome. The current CLI's automatic wait branch only recognizes a top-level `job_id`; a batch receipt can therefore return before completion even with CLI `--wait`.
- **Inline output or a blocking command:** `build-video` aliases to `_dispatch_build_explainer_video`, which awaits its composite and calls child dispatches with `wait=True`, even when the outer request asks for `wait=false`. Mock/local-sidecar and missing-webhook paths can also execute inline. Supervise such CLI processes locally, but backgrounding the client cannot repair RGBA's server request timeout. For a reliable long video workflow, orchestrate job-returning stages and checkpoint their receipts; a durable top-level RGBA composite job would be a separate RGBA change.

`rgba jobs wait` defaults to a 900-second deadline; SDK action waiting defaults to 1900 seconds. A wait timeout stops observation, not the remote render. The current Modal workers have their own 1800-second execution limit. Keep request timeout, local foreground wait, observation deadline, and provider execution limit distinct; extending one does not extend the others.

**Proposed ownership and interface.** Add one launcher-side supervisor and a trusted SQLite control store under the local state root defined in [SESSIONS.md](SESSIONS.md). SQLite jobs, an operation journal, and a durable inbox are additions to that session plan. Keep one agent loop; filesystem, process, and network operations remain behind Runtime and trusted launcher interfaces. Distinguish the agent run (the user's overall task) from its tool jobs (local processes, remote jobs/groups, and later child sessions). Each job records owner/session/run/job IDs, originating tool-call ID, operation and attempt IDs, description, execution kind, process/container identity or remote receipts, status, progress, timestamps, deadlines, next poll time, output/artifact references, and result-consumption checkpoint. Store credentials separately. Register operation intent before launch; persist returned receipts before acknowledging submission.

Expose runtime-backed launch, status/list, bounded output read, wait/yield, and cancel operations. A launch returns a local job ID and a structured pending result promptly. RGBA submission uses its typed adapter or supervised CLI, registering all remote receipts before interpreting the final command outcome. A generic shell launch accepts explicit background execution and a short foreground wait budget; expiration of that budget transfers the same process to supervision. The execution deadline remains a separate limit. Full output is spooled with size/retention limits; model messages contain bounded excerpts and references.

**Completion and continuation.** The required sequence is:

1. Launch and register a tool job. Return the pending tool result with its job ID; the agent can work on independent steps while the supervisor watches the process or polls RGBA.
2. When the agent has no independent work, checkpoint the conversation and yield with the IDs it is waiting for. The run becomes `sleeping`. No model calls, repeated shell status checks, or model step consumption occur while waiting. Subscribe/check pending events transactionally with the sleep transition so a completion during checkpointing cannot be missed.
3. On terminal execution, the owning worker reaps the local child and flushes/persists its output and exit status, or the remote monitor fetches and persists the result. Record terminal status and a deduplicated completion inbox event in one transaction, keyed by local job and execution attempt. Publish a CLI status event after commit. Multiple remote children may complete separately; the group is only terminal when every submitted child is terminal.
4. Wake the same session. If a turn is active, enqueue the event for its next safe boundary after all current tool results; otherwise resume from its checkpoint. Only one loop writer owns a session. Deliver a new structured notification tied to the original job/tool call, rather than a second result for an already-answered tool call. Preserve user input priority and drain completions without starvation.
5. Collect the retained result: expose output and artifact references, and let the agent inspect them and run the next dependent step. Commit the resulting conversation checkpoint together with the inbox acknowledgment and consumption marker. Replaying a notification after a crash must not repeat the continuation's external effects; those steps use the same operation journal. Retain output until consumption and retention policy permit cleanup; collecting a result does not delete an RGBA job.
6. Finalize the agent run only after required jobs are terminal, their results are consumed, and the requested outcome is checked. A video job completing may still require inspection, stitching, or delivery. Replace the current unconditional `done` success with an explicit outcome; pending dependencies yield instead of reporting success.

Remote `completed` is execution status, not proof that the user's task succeeded. [RGBA outcomes.py](../../rgba/cli/src/rgba_cli/outcomes.py) separately rejects partial/failed/canceled payloads and nonempty failed-item lists, preserving successful output. Apply equivalent action-aware checks, including composite `status=error` and expected artifact validation. A QA report's integer `failed` count is a content verdict, not an execution failure. Keep successful child artifacts when a group is partial and resume only the remaining authorized work.

**Monitoring, recovery, and cancellation.** Use run states `queued`, `running`, `sleeping`, `waiting_input`, `paused`, `retrying`, `succeeded`, `failed`, `cancelled`; keep tool execution state and result-consumption state separate. Track an interrupted/unknown local execution explicitly. Budgets and authorization persist across resumed turns; wall deadlines continue during sleep. Budget exhaustion records a stop reason and stops automatic model continuation while outstanding work remains visible.

Poll remote jobs outside the model with bounded concurrency, per-request timeouts, and backoff/jitter (start around 3 seconds, cap around 30 seconds while active). Retry transient observation failures with a bounded error policy; authentication failure or an inaccessible/missing receipt requires resolution, not resubmission. Persist the last successful observation and distinguish stale/unknown status from remote failure. Progress reports show known phase and elapsed time; do not invent percentages. A local observation deadline preserves the remote receipt and reports that the work may still be running.

Claim session turns and monitoring work transactionally with leases and heartbeats; fence stale owners before replacement. Resume remote polling from saved receipts after supervisor/container restart. `rgba jobs list --video <id> --pending --json` helps rediscover active work, but recovery also checks terminal jobs/artifacts because completion may have happened during the outage. A list match alone is not proof of operation identity. RGBA derives idempotency keys and can reset failed jobs on repeated submission; retry/delete also mutate jobs and caches. Reconcile uncertain submissions before any paid retry. If the original operation cannot be identified, pause for resolution rather than promise exactly-once generation.

For local processes, a runtime worker owns the process group and writes output and exit receipts to retained storage; the supervisor owns its lifetime and keeps its container alive while work runs. Client disconnect only detaches the display. Reattach after supervisor restart only if worker identity and execution state can be verified, not from a PID alone. [Session snapshots](SESSIONS.md) do not restore RAM/processes: container loss marks a local command interrupted/unknown and triggers reconciliation, not blind replay. Quiesce writers before snapshots/reset/teardown; isolate background working directories or serialize conflicting writes.

Pause stops new agent steps but continues recording job observations and completions. Cancel stops continuation and requests execution cancellation separately. Local cancellation terminates the process group and reaps it. RGBA's inspected `/sdk/jobs` surface exposes get/list/delete/retry, not a job-cancel endpoint; deleting a job is not cancellation. Report remote work as still running/uncancelled when cancellation is unsupported, and retain receipts for reconciliation. A late completion is recorded but does not restart a cancelled or paused run without an explicit resume.

**CLI first.** Add proposed `jobs list`, `jobs status <id>`, `jobs attach <id>`, `jobs output <id>`, `jobs pause/resume <id>`, and `jobs cancel <id>` commands over the supervisor. Interactive input and completion events share an event loop, so a finished job wakes the agent even while the user is idle. Explicit detach returns a pending run receipt, not task success; reconnect replays events by durable sequence ID. Show job IDs, state, elapsed time, bounded logs, spend, artifacts, and pending input.

Any unresolved submission remains explicit.
